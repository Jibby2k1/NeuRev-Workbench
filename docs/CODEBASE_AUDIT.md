# Codebase Audit

Last updated: 2026-07-13.

This audit focuses on navigability for humans and LLM coding agents, with
secondary attention to maintainability, testability, and dashboard usability.

## Executive Summary

The project has a strong current package center under `neurobench/`, good test
coverage breadth, and a useful documentation set. The main navigability problem
is that some active workflows still live in large scripts or older top-level
modules, while the root README still describes the older layout more prominently
than the current package structure.

The highest-value work is not a rewrite. It is a staged extraction of large
scripts into package modules, plus a small dashboard/report registry so users
and agents can discover the right app or report from an output directory.

## What Is Working

- `neurobench/cli/main.py` is a clear command hub.
- `neurobench/workbench/` has a real package boundary for the dashboard builder,
  server, intermediates, sidecars, and assets.
- Workbench JavaScript source is split under
  `neurobench/workbench/assets/src/`, with the served bundle generated by
  `tools/build_workbench_assets.py`.
- JSON schemas, examples, and model tests provide useful guardrails for
  artifact contracts.
- The docs contain high-value workflow guides for the workbench, raw-video
  reports, template-grid processing, dynamics, and pipeline stages.
- Tests cover many real workflows, not just isolated functions.

## Main Navigability Risks

| Priority | Risk | Evidence | Impact |
| ---: | --- | --- | --- |
| 1 | Gamma CFAR workflow logic is concentrated in one large script. | `tools/prepare_gamma_cfar_workbench_run.py` is about 3,557 lines. | Hard for humans/LLMs to modify safely; hidden coupling between conversion, sweep execution, and dashboard attachment. |
| 2 | The root README structure is stale. | It still foregrounds `core/`, `evaluation/`, and `reporting/`, while current work largely lives under `neurobench/`. | New contributors and agents start in the wrong place. |
| 3 | Dashboard/report discovery is output-specific. | Workbench apps, Gamma CFAR sweeps, and dynamics dashboards use different implicit file conventions. | Users must remember paths instead of asking the repo to locate the right dashboard. |
| 4 | Large browser modules remain broad. | `20_review_core.js` is about 3,492 lines; `30_architecture_lab.js` is about 2,481 lines. | UI changes are harder to review; LLM edits are more likely to touch unrelated behavior. |
| 5 | Dynamics orchestration modules are large and high-stakes. | `overnight_sweep.py`, `multi_horizon.py`, `concept_tests.py`, `comparison.py`, and `report.py` are all over 1,000 lines. | Refactors can affect expensive GPU runs and reports unless split behind tests. |
| 6 | Legacy top-level modules coexist with newer package modules. | `core/`, `evaluation/`, and `reporting/` remain beside `neurobench/`. | It is unclear which implementation should be extended. |

## Recommended Target Structure

This is a target for staged migration, not a requirement for a single PR.

```text
neurobench/
  dashboards/
    registry.py          # find dashboards/reports from a dataset or output root
    manifest.py          # common dashboard_manifest.json helpers
  gamma_cfar/
    dataset.py           # TIFF/MP4 conversion and starter review data
    specs.py             # sweep spec builders
    runners.py           # CPU/GPU grid runners
    attach.py            # workbench attachment, sidecars, run metadata
    reports.py           # Gamma CFAR brief helpers
  workbench/
    builder.py
    server.py
    assets/
  dynamics/
    dashboards.py        # shared dashboard artifact helpers currently in tools
```

`tools/` should stay as a stable command surface, but implementation should
move into importable modules once a script becomes large or widely reused.

## Refactor Plan

### Phase 1: Navigation And Discovery

1. Keep `docs/CODEBASE_NAVIGATION.md` current and link it from onboarding docs.
2. Add `dashboard_manifest.json` generation to all new dashboard-producing
   workflows.
3. Add a `neurobench dashboard status` command that prints:
   - dashboard type
   - app/report paths
   - recommended serve command
   - missing files
4. Add a `neurobench dashboard serve` command that starts the right local server
   for a dataset root.

### Phase 2: Gamma CFAR Extraction

1. Move TIFF/MP4 conversion and starter review data into
   `neurobench/gamma_cfar/dataset.py`.
2. Move sweep spec builders into `neurobench/gamma_cfar/specs.py`.
3. Move CPU/GPU fast-grid runners into `neurobench/gamma_cfar/runners.py`.
4. Move attachment and sidecar logic into `neurobench/gamma_cfar/attach.py`.
5. Keep `tools/prepare_gamma_cfar_workbench_run.py` as a compatibility CLI.
6. Add focused tests for each extracted module before deleting duplicated code.

### Phase 3: Dashboard Code Boundaries

1. Add `neurobench/dashboards/manifest.py` and use it in Gamma CFAR first.
2. Move grid dashboard artifact helpers from
   `tools/build_grid64_dashboard_artifacts.py` into an importable module.
3. Keep script wrappers stable for existing notebooks and lab usage.
4. Add a dashboard registry test with small fixture directories.

### Phase 4: Workbench UI Split

1. Split `20_review_core.js` by responsibility:
   - ROI list/model state
   - canvas drawing
   - trace panel
   - event controls
   - review filters and sort
2. Split `30_architecture_lab.js` into saved architectures, planning, run
   comparison, and import/export.
3. Keep the ordered bundle builder until the static-file workflow is replaced.
4. Add browser or JSON smoke tests for the high-risk routes.

### Phase 5: Dynamics Stabilization

1. Avoid broad refactors in `neurobench/dynamics/overnight_sweep.py` while
   long-running sweeps are active or recently stopped.
2. Extract pure helpers first: manifest planning, progress parsing, health
   summaries, and launch-readiness formatting.
3. Keep GPU execution and resume behavior covered by focused tests before
   changing runner control flow.

  - NeuronReview app root

## Test And Validation Improvements

- Add a dashboard manifest unit test using a tiny fixture app.
- Add a Gamma CFAR attachment test that verifies:
  - self-template metadata is preserved
  - recommended runs are discoverable
  - sidecar paths are relative to the app where appropriate
- Add a CLI smoke test for `dashboard status` once that command exists.
- Add `tools/build_workbench_assets.py --check` to the focused workbench test
  path.
- Keep expensive GPU tests opt-in and separate from CPU-safe CI.

## LLM-Oriented Guidelines

- Put "start here" docs near the code they describe.
- Prefer smaller importable functions over long script-local helpers.
- Use explicit JSON manifests to connect generated artifacts instead of relying
  on naming conventions alone.
- Keep compatibility wrappers when moving code; LLMs and lab notebooks often
  reuse command strings from prior runs.
- Avoid broad renames in output paths unless a migration helper exists.
- Include concrete file paths in reports and markdown output.

### Fixed P0 Resource-Initialization Finding

The v1 Spon diagnostic exposed a separate P0 issue: `neurobench/cli/main.py`
eagerly registered every command group, so invoking the focused experiment CLI
could import NumPy/SciPy/PyTorch through unrelated dynamics commands before the
experiment applied its two-thread CPU limit. The observed CPU and resident-memory
oversubscription made the nominal manifest cap unreliable.

The CLI now lazy-loads group registrars, and
`neurobench/cli/experiment.py` reads the lightweight manifest fields and sets
OpenMP/BLAS limits plus `CUDA_VISIBLE_DEVICES` before importing the scientific
experiment package. The v2 preflight also budgets an empirical 640 MiB
scientific-runtime overhead plus 32 MiB enforcement headroom. During execution,
the runner samples Linux `VmRSS`/`VmHWM` and fails if the 1,024 MiB cap is
exceeded. These changes make import order, estimation, and live enforcement
part of the resource contract rather than relying on configuration intent
alone.

### Structure Applied In This Pass

The Spon experiment is isolated under
`neurobench/experiments/soma_excitation/` rather than extending the 3,558-line
Gamma workbench script or the stopped sweep runner. It has separate modules for:

- validated configuration and resource preflight;
- quiet-baseline dark-core geometry;
- streamed positive-excitation evidence;
- frozen batch-1 transfer evaluation;
- orchestration/reporting behind a thin CLI.

The shared video reader now supports absolute half-open frame ranges for NumPy
and page-addressable TIFF sources. The NumPy cache was checked for matching
shape/dtype and sampled TIFF pages were byte-identical; this is deliberately
described as sampled verification, not an exhaustive frame comparison. CFAR
parameter validation rejects invalid probabilities and zero epsilon. Focused
tests protect frame 1900 mapping, control/event separation, chunk invariance,
zone geometry, checkpoint loading, and online metrics.

Scientifically, the package keeps dark-core anatomy separate from event
evidence. Dark cores are anatomical background anchors. The one-sided CFAR lane
detects positive local excursions, while a separate half-wave positive
quiet-baseline residual is the primary broad-excitation lane because a local
background estimator can suppress spatially broad changes.

### Intentional Non-Changes

This pass does not split the active dynamics monoliths, relocate the shared
hybrid model, rewrite the historical Gamma artifacts, or remove the 81 GiB Spon
tree. Those are valuable follow-up refactors, but combining them with a new
scientific experiment would enlarge the regression surface and obscure
provenance. The new package demonstrates the preferred boundary first.
